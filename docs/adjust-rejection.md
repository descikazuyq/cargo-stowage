# 配载被拒绝时怎样读懂错误

本文说明 `stowage` 包正式提交（`Adjust`）在一种特定情形下返回的错误：
**一批安排里的每条装卸操作本身都合法，但整批安排全部完成后的最终
配载违反了承重或混装限制**——某舱超重、不同目的地货物违规共舱，或
重量合计溢出 `int64`。这时调用方拿到的是什么、应该核对哪个对象、
怎样看全部问题，以及为什么拒绝之后查不到"装了一半"的状态。

文中示例均为完整可运行的 Go 代码，与
`stowage/example_adjust_rejection_test.go` 中的示例一一对应，每个
示例都从新建的空登记处开始、包含必要的初始化与错误处理，可用
`go test ./...` 直接验证输出，不依赖其他文档中的示例。

> 如果失败发生在逐条操作校验阶段（货物或舱位不存在、货物已装载/
> 未装载状态不符、同一批中重复操作、移动到原舱位等），返回的同样是
> `*stowage.Error`，但在最终配载评估之前就已产生，不适用本文的选择
> 规则；这类错误的读法可参照[提交前核对配载安排](preview-check.md)
> 中"操作不合法"一节。

## 失败时只有一个结构化错误，没有成功结果

这种情形下 `Adjust(adjustmentID, ops)` 返回 `nil` 结果加一个结构化
错误 `*stowage.Error`——**没有成功结果可供读取**，用 `errors.As`
取出错误后按四个字段读：

- `Kind`：错误类别（中文说明由 `Kind.String()` 给出），决定后面去
  核对什么对象。本文涉及三种：
  - `ErrOverweight`（超重）：舱位预计总重量超过最大承重；
  - `ErrMixedLoading`（混装冲突）：不同目的地货物共舱，但其中有
    货物不允许混装；
  - `ErrOverflow`（重量溢出）：舱位重量合计超过 `int64` 可表示范围。
- `ID`：**涉及对象的编号**。超重与重量溢出时是舱位编号；混装冲突
  时是货物编号。读 `ID` 前先确认 `Kind`。
- `AdjustmentID`：涉及的调整编号（去掉首尾空白后的值），便于在
  重试、日志、对账中定位是哪一次提交被拒。
- `Error()`：可直接阅读的中文说明，舱位、货物与关键数值都在里面。

一次提交即使让**多个舱位**同时违规、一个舱位同时有**两类**问题，
`Adjust` 也只返回这一个错误。报哪一个由最终配载决定，规则固定：

1. **先按舱位编号字典序，选最靠前的违规舱位**；
2. **同一舱位同时有重量问题与混装问题时，先报告重量问题**
   （重量溢出与超重都属于重量问题）；
3. 选择只取决于最终配载本身，**与操作的排列顺序无关**，也与舱位、
   货物的登记先后无关——把清单里的操作重排后再提交，报的还是同
   一条。

想看全部问题而不只是第一条，对同一批安排使用 `Preview`（见下文）。

## 主示例：两个舱位同时违规，为什么报前一个舱的混装

从空登记处开始：C1 承重 1000 千克，C2 承重 50 千克。C1 里已有两
件同去上海、都不允许混装的货物 G2、G7（同目的地共舱合法，各 10
千克）；另有未装载的 G1（10 千克，去北京，**允许**混装），以及
G3、G4（各 30 千克，同目的地，都允许混装）：

```go
reg := stowage.NewRegistry()
reg.RegisterCompartment("C1", 1000)
reg.RegisterCompartment("C2", 50)
reg.RegisterCargo("G2", 10, "上海", false)
reg.RegisterCargo("G7", 10, "上海", false)
reg.RegisterCargo("G1", 10, "北京", true)
reg.RegisterCargo("G3", 30, "X", true)
reg.RegisterCargo("G4", 30, "X", true)
_, err := reg.Adjust("init", []stowage.Op{
    {Kind: stowage.OpLoad, CargoID: "G2", Target: "C1"},
    {Kind: stowage.OpLoad, CargoID: "G7", Target: "C1"},
})
// err == nil：初始配载完成，G2、G7 在 C1，共 20/1000 千克。
```

提交一批安排：把 G3、G4 装入 C2，把 G1 装入 C1。注意 **C2 的两条
操作故意写在最前面**：

```go
ops := []stowage.Op{
    {Kind: stowage.OpLoad, CargoID: "G4", Target: "C2"},
    {Kind: stowage.OpLoad, CargoID: "G3", Target: "C2"},
    {Kind: stowage.OpLoad, CargoID: "G1", Target: "C1"},
}
res, err := reg.Adjust("bad-batch", ops)
```

这批操作每一条都合法，但完成后的最终配载有两个问题：

- **C1 混装冲突**：G2、G7 去上海且不允许混装，G1 去北京。不同目的
  地共舱要求所有货物都允许混装，G2、G7 不满足。重量只有 30 千克，
  远低于 1000 千克承重。
- **C2 超重**：G3 + G4 合计 60 千克，超过承重 50 千克。同目的地，
  没有混装问题。

正式提交只报告其中一条（对应
`Example_adjustRejectionEarliestCompartment`）：

```
有成功结果: false
错误类别: 混装冲突
涉及对象: G2
调整编号: bad-batch
中文说明: 舱位 C1 存在不同目的地货物，但货物 G2 不允许混装
```

读法：

- 舱位按编号字典序选择，`C1` 在 `C2` 前面，所以**即使 C2 的操作写
  在清单最前面、即使 C2 超重更多**，报告的仍是 C1 的混装冲突。
  把操作顺序整个倒置（G1 的装载写到第一条）再用另一个编号提交，
  结果不变：

  ```
  == 操作顺序倒置后再提交 ==
  错误类别: 混装冲突
  涉及对象: G2
  ```

- 混装冲突的 `ID` 是**最终舱内不允许混装的货物中，编号字典序最靠
  前的一件**。这里违规货物集合是原舱的 `{G2, G7}`，最靠前的是
  **G2**；它是**原本就在 C1 里的货物，不是本次新加入的 G1**——G1
  允许混装，根本不在违规集合内。所以"被点名的货物"回答的是"哪件
  货物的混装许可与最终局面冲突"，而不是"哪条操作惹的祸"。中文说明
  同时指出冲突舱位 C1，对象与舱位都能直接定位。

## 三类错误分别核对什么

### 超重：对象是舱位，说明带预计总重量与最大承重

C1 承重 50 千克，G1 重 60 千克、去上海、不允许混装，G2 重 40 千克、
去北京、允许混装；两件一起装入后合计 100 千克，既超重又构成混装
（对应 `Example_adjustRejectionWeightBeforeMixed`）：

```go
res, err := reg.Adjust("wm-1", []stowage.Op{
    {Kind: stowage.OpLoad, CargoID: "G2", Target: "C1"},
    {Kind: stowage.OpLoad, CargoID: "G1", Target: "C1"},
})
var serr *stowage.Error
if errors.As(err, &serr) {
    fmt.Println("错误类别:", serr.Kind)   // 超重
    fmt.Println("涉及对象:", serr.ID)     // C1
    fmt.Println("调整编号:", serr.AdjustmentID)
    fmt.Println("中文说明:", serr)
}
```

```
有成功结果: false
错误类别: 超重
涉及对象: C1
调整编号: wm-1
中文说明: 舱位 C1 总重量 100 千克超过最大承重 50 千克
```

同一舱位两类问题并存时先报告重量：`Kind` 是 `ErrOverweight`，`ID`
是**舱位 C1**，而不是任何一件货物；中文说明直接给出**预计总重量
100 千克与最大承重 50 千克**，差多少、该卸哪件，照这两个数核对
即可。

### 混装冲突：对象是编号最靠前的不允许混装货物

如上节主示例所示：`Kind` 是 `ErrMixedLoading` 时，`ID` 是一件
**货物**编号——最终舱内全部不允许混装货物里字典序最靠前的那件，
可能是原舱货物，也可能是本批移入的货物，与谁最后进舱无关；中文
说明固定为"舱位 X 存在不同目的地货物，但货物 Y 不允许混装"，舱位
从说明里读，货物从 `ID` 读。

### 重量溢出：对象仍是舱位，且先于同舱混装，不引用合计数值

两件货物重量都取 `math.MaxInt64`：G1（上海，不允许混装）已在舱内，
再把 G2（北京，允许混装）装入，预计合计超过 `int64` 可表示范围，
同时目的地也不同（对应 `Example_adjustRejectionOverflowBeforeMixed`）：

```
有成功结果: false
错误类别: 重量溢出
涉及对象: C1
调整编号: ov-1
中文说明: 舱位 C1 重量合计超过 int64 可表示范围
```

- 溢出同样属于重量问题，**先于同一舱位的混装冲突**报告；`Kind` 是
  `ErrOverflow`，`ID` 仍是舱位 C1。
- 预计合计已经无法用 `int64` 表示，所以说明里**不出现那个合计
  数值**（也没有预计已用、剩余、超出量可读）——不要指望从错误文本
  里解析一个不存在的总数；能确定的就是"该舱按本批安排完成后合计
  溢出"。核对时从舱内各件货物的登记重量入手。

| 错误类别 | `Kind` | `ID` 指向 | 中文说明可读出 |
| --- | --- | --- | --- |
| 超重 | `ErrOverweight` | 舱位 | 舱位、预计总重量、最大承重 |
| 混装冲突 | `ErrMixedLoading` | 货物（最终舱内不允许混装且编号最靠前） | 冲突舱位与该货物 |
| 重量溢出 | `ErrOverflow` | 舱位 | 舱位；只说明合计超出 int64 范围，无合计数值 |

## 同一批安排用 Preview 可以看到全部拒绝原因

`Adjust` 的单条错误是"按固定顺序选出的第一条"，**不表示整批只有
一个问题**。对同一批操作先调用只读的 `Preview`，`Rejections` 会
一次列全全部违规舱位的全部原因，顺序也是舱位编号字典序、同舱先
重量后混装，与正式提交的选择一致。

主示例那批操作（C1 混装、C2 超重）的预览结果：

```
可提交: false
拒绝原因 1: C1 混装冲突
拒绝原因 2: C2 超重
```

同舱超重与混装并存的那批操作，预览则保留同一舱位的两条：

```
同一批 Preview 的全部原因: C1/超重 C1/混装冲突
```

因此修安排时的典型分工是：**`Preview` 负责看全面**（全部原因、
受影响舱位前后的完整清单），**`Adjust` 负责正式生效**；被 `Adjust`
拒绝后若想一次了解全部阻碍，对同一批操作补一次 `Preview` 即可，
预览不改变状态、不占用编号。预览的完整读法见
[提交前核对配载安排](preview-check.md)。

## 拒绝后查询：仍是提交前的配载，没有部分装卸

最终配载违规与某条操作本身不合法一样，使**整次调整不生效**：校验
在任何装卸正式应用之前完成，不存在"先装了几件、发现超重再回退"。
主示例被拒之后查询，看到的是提交前的归属与占用：

```
== 拒绝后查询 ==
G1: （未装载）
G2: C1
G3: （未装载）
G4: （未装载）
G7: C1
C1: 已用 20 千克、剩余 980 千克
C2: 已用 0 千克、剩余 50 千克
```

- 本批要装的 G1、G3、G4 **都仍未装载**，C2 仍是空舱；原舱的 G2、
  G7 仍在 C1，C1 仍是 20/1000 千克。
- 即使清单里混着本可单独成功的操作（例如一批里同时有一次合法卸下
  和一次导致超重的移动），被拒后那条合法操作同样**没有生效**，
  查询结果与提交前逐项一致。不要把失败理解成"部分装卸已完成"。
- 被拒的调整**不占用调整编号**：把安排修正后沿用同一编号提交，是
  一次正常的全新生效，而不是取回旧结果。编号在成功与失败两种情形
  下的完整行为，见
  [正式提交调整与同一编号的再次提交](commit-adjustment.md)。

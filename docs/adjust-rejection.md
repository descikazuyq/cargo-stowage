# 配载被拒绝时怎样读懂错误

本文说明 `stowage` 包正式提交（`Adjust`）被**配载限制**拒绝时，调用方
如何读懂返回的结构化错误：一次失败报告了什么、应核对哪个对象，以及
它与 `Preview` 列出的全部拒绝原因是什么关系。

这里的"被拒绝"专指一种情况：一批安排中**每条装卸操作本身都合法**
（货物与舱位都存在、货物状态与操作相符、没有重复操作），但全部操作
完成后的**最终配载**违反承重或混装限制——某个舱位总重量超过承重，
或不同目的地的货物共舱而其中有货物不允许混装。操作本身不合法
（逐条校验失败）与调整编号冲突是另外两类失败，分别见
[提交前核对配载安排](preview-check.md)与
[正式提交调整与同一编号的再次提交](commit-adjustment.md)。

文中示例均为完整可运行的 Go 代码，与
`stowage/example_adjust_rejection_test.go` 中的示例一一对应，每个
示例都从新建的空登记处开始、包含必要的初始化与错误处理，可用
`go test ./...` 直接验证输出，不依赖其他文档中的示例。

## 一次失败只报告一条：选中哪一条是固定的

最终配载违规时，`Adjust` **不返回成功结果**，只返回一个结构化错误
`*stowage.Error`。一批安排可能同时违反多处限制，但正式提交每次只报告
其中一条，选择规则是固定的：

1. 先按**舱位编号字典序**选出最靠前的违规舱位；
2. 同一舱位同时存在重量问题（超重或重量溢出）与混装问题时，**先报告
   重量问题**。

因此，前一个舱位只有混装冲突、后一个舱位超重时，报告的是**前一个舱位
的混装冲突**，而不是后一个舱位的超重。这个选择只看最终配载与舱位
编号，**改变清单中操作的排列顺序不会改变它**——同一批安排无论怎么
排列，读到的一定是同一条错误。

## 错误怎么读：类别、涉及对象、调整编号、中文说明

用 `errors.As` 取出 `*stowage.Error` 后，四个信息各有分工：

- `Kind`：错误类别。配载限制拒绝有三种——`ErrOverweight`（超重）、
  `ErrMixedLoading`（混装冲突）、`ErrOverflow`（重量溢出）。
- `ID`：**涉及对象**的编号，含义随类别而定（见下表）。
- `AdjustmentID`：本次提交的调整编号（去掉首尾空白后的值），便于在
  日志与对账中定位是哪一次提交被拒绝。
- `Error()`：可直接阅读的中文说明，包含判断所需的关键数值与对象。

| `Kind` | `ID` 指向 | 中文说明包含 |
| --- | --- | --- |
| `ErrOverweight` 超重 | **舱位** | 预计总重量与最大承重（如"舱位 C1 总重量 70 千克超过最大承重 50 千克"） |
| `ErrMixedLoading` 混装冲突 | **货物**：最终舱内不允许混装且编号字典序最靠前的一件 | 冲突舱位与该货物（如"舱位 C1 存在不同目的地货物，但货物 G1 不允许混装"） |
| `ErrOverflow` 重量溢出 | **舱位** | 只指出舱位重量合计超过 int64 可表示范围，**不引用无法表示的预计合计数值** |

两点容易误读：

- 混装错误指出的货物**不一定在本批安排里**。判断针对的是最终配载，
  不允许混装的货物可能原本就在舱内；此时 `ID` 指向那件**原舱货物**，
  而不是本次新加入的货物。核对时不要只盯着本批清单。
- 重量合计超过 int64 可表示范围时是独立的 `ErrOverflow` 类别，仍指向
  舱位、仍先于同舱的混装问题被报告；因为预计合计已无法用 int64 表示，
  说明中不会出现合计数值，只有舱位编号。

## 主示例：两个舱位同时违规，正式提交选中哪一条

从空登记处开始（对应 `Example_adjustRejectedPicksFirstCompartment`）：
舱位 `C1` 承重 100 千克，已装 `G1`（60 千克、目的地上海、**不允许
混装**）；舱位 `C2` 承重 50 千克，已装 `G2`（40 千克、目的地北京、
允许混装）。另有两件已登记但未装载的货物：`G3`（30 千克、目的地
广州、允许混装）、`G4`（20 千克、目的地上海、允许混装）：

```go
reg := stowage.NewRegistry()
if err := reg.RegisterCompartment("C1", 100); err != nil {
    panic(err)
}
if err := reg.RegisterCompartment("C2", 50); err != nil {
    panic(err)
}
if err := reg.RegisterCargo("G1", 60, "上海", false); err != nil {
    panic(err)
}
if err := reg.RegisterCargo("G2", 40, "北京", true); err != nil {
    panic(err)
}
if err := reg.RegisterCargo("G3", 30, "广州", true); err != nil {
    panic(err)
}
if err := reg.RegisterCargo("G4", 20, "上海", true); err != nil {
    panic(err)
}
// 初始装载：G1 入 C1、G2 入 C2。
if _, err := reg.Adjust("load-1", []stowage.Op{
    {Kind: stowage.OpLoad, CargoID: "G1", Target: "C1"},
    {Kind: stowage.OpLoad, CargoID: "G2", Target: "C2"},
}); err != nil {
    panic(err)
}
```

现在提交调整 `plan-1`：把 `G3` 装入 `C1`、`G4` 装入 `C2`。两条操作
本身都合法，但完成后的最终配载里两个舱位都违规：

- `C1`：60+30=90 千克不超重，但上海（`G1`）与广州（`G3`）共舱，
  而 `G1` 不允许混装——**只有混装冲突**；
- `C2`：40+20=60 千克超过承重 50 千克——**超重**（`G2`、`G4` 都允许
  混装，不构成混装冲突）。

```go
ops := []stowage.Op{
    {Kind: stowage.OpLoad, CargoID: "G3", Target: "C1"},
    {Kind: stowage.OpLoad, CargoID: "G4", Target: "C2"},
}
res, err := reg.Adjust("plan-1", ops)
fmt.Println("有结果返回:", res != nil)
var serr *stowage.Error
if errors.As(err, &serr) {
    fmt.Println("拒绝原因:", serr.Kind)
    fmt.Println("涉及编号:", serr.ID)
    fmt.Println("调整编号:", serr.AdjustmentID)
    fmt.Println("说明:", serr)
}
```

```
有结果返回: false
拒绝原因: 混装冲突
涉及编号: G1
调整编号: plan-1
说明: 舱位 C1 存在不同目的地货物，但货物 G1 不允许混装
```

读法：

- **为什么报混装而不是超重？** `C1` 与 `C2` 都违规，按舱位编号字典序
  `C1` 靠前，报告 `C1` 的问题；`C1` 只有混装冲突，所以类别是
  `ErrMixedLoading`。`C2` 的超重这次不报告，但不等于不存在（见下节
  的预览对照）。
- **为什么涉及编号是 `G1`？** 混装错误指向最终舱内不允许混装且编号
  字典序最靠前的货物。`C1` 里不允许混装的只有原舱的 `G1`；本批新
  加入的 `G3` 允许混装，根本不在违规集合内。被指出的是**原舱货物**，
  不是本次新加入的货物。
- `AdjustmentID` 是 `plan-1`，说明这句中文同时指出冲突舱位 `C1` 与
  违规货物 `G1`。

改变操作排列不会改变这个选择。失败的调整不占用编号（见
[正式提交调整与同一编号的再次提交](commit-adjustment.md)），把两条
操作倒置后沿用 `plan-1` 再提交，得到的仍是同一条错误：

```go
_, err = reg.Adjust("plan-1", []stowage.Op{
    {Kind: stowage.OpLoad, CargoID: "G4", Target: "C2"},
    {Kind: stowage.OpLoad, CargoID: "G3", Target: "C1"},
})
```

```
倒置顺序后拒绝原因: 混装冲突
倒置顺序后涉及编号: G1
```

## 同一批安排用 Preview 列全所有拒绝原因

正式提交的单条错误**不表示只有一个问题**。同一批安排交给 `Preview`
（只读、不占编号），`Rejections` 会按"舱位编号字典序、同舱先重量后
混装"一次列全——这正是正式提交选取第一条时使用的顺序：

```go
prev, err := reg.Preview(ops) // err == nil：每条操作本身合法
fmt.Println("预览可提交:", prev.Submittable)
```

```
预览可提交: false
预览原因: 舱位 C1 混装冲突，不允许混装的货物: [G1]
预览原因: 舱位 C2 超重 10 千克（60/50）
```

对照可见：正式提交报告的正是预览列出的第一条（`C1` 混装冲突），而
`C2` 超重 10 千克（60/50）这条只在预览里出现。修正安排时建议先用
`Preview` 看全所有问题，避免改掉一条、提交又撞上下一条。

## 同舱超重与混装并存：重量优先

再看一个更短的例子（对应 `Example_adjustRejectedWeightBeforeMixed`）：
舱位 `C1` 承重 50 千克，已装 `G1`（40 千克、目的地上海、不允许混装）；
本批把 `G2`（30 千克、目的地北京、允许混装）装入 `C1`。最终配载
70/50 千克**超重**，同时上海与北京共舱而 `G1` 不允许混装——同一个
舱位两种问题并存，正式提交先报告重量问题：

```
拒绝原因: 超重
涉及编号: C1
调整编号: add-g2
说明: 舱位 C1 总重量 70 千克超过最大承重 50 千克
预览原因: 舱位 C1 超重 20 千克（70/50）
预览原因: 舱位 C1 混装冲突，不允许混装的货物: [G1]
```

- 超重错误 `ID` 指向**舱位** `C1`，说明里的 70 千克是**预计总重量**
  （最终配载的合计），50 千克是最大承重。
- 预览把同舱的两条原因都列出，顺序同样是先重量后混装；正式提交取的
  是第一条。

## 被拒绝后查询：仍是提交前的配载

配载限制拒绝是**整批不生效**：不存在"部分装卸已完成"的中间状态。
主示例被拒绝后立刻查询，看到的仍是提交前的货物归属与舱位占用：

```
当前 G3: （未装载）
当前 G4: （未装载）
当前 C1: [G1]，已用 60 千克、剩余 40 千克
当前 C2: [G2]，已用 40 千克、剩余 10 千克
```

`G3`、`G4` 仍未装载，`C1`、`C2` 的清单与已用重量都与提交前一致。
不要因为错误只提了 `C1` 就以为 `C2` 的装载已经生效——整批都没有
生效。修正安排后用同一编号重新提交即可（失败不占用编号）；想确认
当前状态，以 `Cargo`、`Compartment` 查询为准。

# 正式提交调整与同一编号的再次提交

本文说明 `stowage` 包正式提交（`Adjust`）成功后返回什么、如何读懂
返回的变化记录，以及围绕**同一调整编号的再次提交**调用方最容易混淆的
几件事：为什么再次提交会拿到一份旧结果、什么才算"原内容"、编号冲突
时错误怎么读、第一次就失败的调整为什么可以沿用原编号。

文中示例均为完整可运行的 Go 代码，与
`stowage/example_adjust_test.go` 中的示例一一对应，每个示例都从新建
的空登记处开始、包含必要的初始化与错误处理，可用 `go test ./...`
直接验证输出，不依赖其他文档中的示例。

## 先记住一条主线：结果是历史记录，查询才是当前状态

`Adjust(adjustmentID, ops)` 成功时做两件事：

1. 按安排改变当前配载（货物归属、舱位已用重量）；
2. 把**这次成功当刻的变化记录**（`AdjustmentResult`）连同调整编号
   一起保存下来。

之后以**同一编号、同一内容**再次提交，登记处不会重新执行那些操作，
而是把首次保存的结果**原样返回**。因此：

- `AdjustmentResult`（`CargoChanges`、`CompartmentChanges`）回答的是
  "**首次成功那次**发生了什么变化"，是一份历史快照，不随后续配载
  变化而改变；
- `Cargo`、`Compartment` 查询回答的是"**查询当刻**货物在哪、舱位
  装了多重"。

两者可能描述完全不同的局面。旧结果可以安全地重复取回，但**不要把它
当成刚刚发生的配载变化**；想确认当前配载，以查询为准。

## 主示例：装入、卸下，再按原编号重交装载

从空登记处开始：登记一个承重 100 千克的舱位 `C1` 和一件 30 千克的
货物 `G1`（对应 `Example_adjustResubmitSameContent`）：

```go
reg := stowage.NewRegistry()
if err := reg.RegisterCompartment("C1", 100); err != nil {
    panic(err)
}
if err := reg.RegisterCargo("G1", 30, "上海", false); err != nil {
    panic(err)
}
```

第一次调整 `load-g1` 把 `G1` 装入 `C1`：

```go
loadOps := []stowage.Op{{Kind: stowage.OpLoad, CargoID: "G1", Target: "C1"}}
first, err := reg.Adjust("load-g1", loadOps)
if err != nil {
    panic(err)
}
```

返回结果记录的是首次成功时的变化——货物从未装载变为 `C1`，舱位重量
从 0 变为 30 千克：

```
调整编号: load-g1
货物 G1: （未装载） -> C1
舱位 C1 重量: 0 -> 30 千克
```

- `CargoChanges` 给出每件货物调整前后的所属舱位，按货物编号字典序
  排列；空字符串表示未装载。
- `CompartmentChanges` 给出每个受影响舱位调整前后的总重量，按舱位
  编号字典序排列。

接着用**另一个调整编号** `unload-g1` 把货物卸下，然后查询当前状态：

```go
if _, err := reg.Adjust("unload-g1", []stowage.Op{
    {Kind: stowage.OpUnload, CargoID: "G1"},
}); err != nil {
    panic(err)
}
g1, _ := reg.Cargo("G1")
c1, _ := reg.Compartment("C1")
```

```
当前 G1: （未装载）
当前 C1: 已用 0 千克、剩余 100 千克
```

现在配载已经回到空舱。随后按**第一次的编号和原内容**再次提交装载：

```go
again, err := reg.Adjust("load-g1", loadOps)
if err != nil {
    panic(err)
}
```

这次调用同样成功，但返回的是**第一次成功时保存的那份记录**：

```
调整编号: load-g1
货物 G1: （未装载） -> C1
舱位 C1 重量: 0 -> 30 千克
```

表面上看，这份结果与首次提交一模一样，好像货物又被装了一次。没有。
再次提交不会重新执行操作，紧接着查询可以确认配载并没有改变：

```
当前 G1: （未装载）
当前 C1: 已用 0 千克、剩余 100 千克
```

货物仍未装载，舱位已用重量仍是 0、剩余 100 千克。同一份输出出现在
两个时刻，含义却不同：首次提交时它是**刚发生的变化**；再次提交时它
只是**首次变化的回放**。区分两者只需对照查询——查询永远反映调用时
的状态。

这也意味着：重复提交对当前配载是安全的无操作。网络重试、消息重复
投递等场景下，调用方可以放心用同一编号重发同一批安排，装卸不会被
重复执行；首次结果随时可以原样取回（调用方拿到的是副本，修改它不
影响登记处保存的记录）。

## 什么算"原内容"

再次提交能否被识别为原调整，不看操作对象当前在哪，只比较**提交内容
本身**。规则如下：

- 比较的是每条操作的**货物编号**、**操作种类**（装载/卸下/移动），
  以及**装载和移动的目标舱位**；三者都相同才算同一内容。
- **操作的排列顺序不影响判断**：同一批操作先写哪条都一样。
- 货物编号、舱位编号都按**去掉首尾空白后**的值比较。
- 调整编号同样**去掉首尾空白后**逐字符比较，并且**区分大小写**。
- **卸下操作填写的目标值不参与比较**——卸下在执行时本来就忽略目标，
  无论填的是已登记舱位、不存在的舱位还是空白，都不影响内容判断。

下例中，首次调整 `batch-1` 一次装入两件货物，之后另有调整把它们都
卸下；再次提交时把编号的首尾空白换成制表符、把两条操作顺序倒置，
仍识别为同一次调整（对应 `Example_adjustResubmitEquivalentContent`）：

```go
first, err := reg.Adjust("  batch-1  ", []stowage.Op{
    {Kind: stowage.OpLoad, CargoID: "G1", Target: "C1"},
    {Kind: stowage.OpLoad, CargoID: "G2", Target: "C1"},
})
// ... 另一次调整 unload-all 卸下 G1、G2 ...
reversed, err := reg.Adjust("\tbatch-1\t", []stowage.Op{
    {Kind: stowage.OpLoad, CargoID: "G2", Target: "C1"},
    {Kind: stowage.OpLoad, CargoID: "G1", Target: "C1"},
})
```

两次返回的都是首次记录（`0 -> 50 千克`），而不是按当前空舱重新算出
的结果；卸下调整即使给操作填上不存在的目标舱位，同样只回放首次记录：

```
首次结果：
调整编号: batch-1
货物 G1: （未装载） -> C1
货物 G2: （未装载） -> C1
舱位 C1 重量: 0 -> 50 千克
逆序再次提交结果：
调整编号: batch-1
货物 G1: （未装载） -> C1
货物 G2: （未装载） -> C1
舱位 C1 重量: 0 -> 50 千克
卸下带目标再次提交，编号: unload-all
货物 G1: C1 -> （未装载）
货物 G2: C1 -> （未装载）
当前 G1: （未装载）
当前 G2: （未装载）
当前 C1: 已用 0 千克、剩余 100 千克
```

### 编号区分大小写：大小写不同就是另一次调整

去空白后编号逐字符比较且区分大小写，`load-g1` 与 `Load-G1` 是两个
互不相干的编号（对应 `Example_adjustResubmitCaseSensitiveID`）。货物
已被卸下后，用大小写不同的编号提交同样的装载，登记处视为**一次全新
调整**，会真正装货：

```
新编号调整：
调整编号: Load-G1
货物 G1: （未装载） -> C1
舱位 C1 重量: 0 -> 30 千克
当前 G1: C1
当前 C1: 已用 30 千克、剩余 70 千克
```

而此时原编号 `load-g1` 再次提交仍只回放首次结果，不会二次装载：

```
原编号回放编号: load-g1
当前 G1: C1
当前 C1: 已用 30 千克、剩余 70 千克
```

想取回首次结果，只能逐字符使用原编号；想真正再执行一次安排，要换
一个从未成功使用过的编号。

## 同一编号换成不同内容：调整编号冲突

编号一旦随某次调整**成功**保存，就与那次的内容绑定。用同一编号提交
**不同内容**——换了货物、换了操作种类、改变装载或移动的目标舱位、
增减操作条数——都会被拒绝，错误为结构化的 `*stowage.Error`，
`Kind` 是 `ErrAdjustmentIDConflict`（对应 `Example_adjustIDConflict`）：

```go
// load-g1 已成功用于“装载 G1 到 C1”。
_, err := reg.Adjust("load-g1", []stowage.Op{
    {Kind: stowage.OpUnload, CargoID: "G1"},
})
var serr *stowage.Error
if errors.As(err, &serr) {
    fmt.Println("拒绝原因:", serr.Kind)         // 调整编号冲突
    fmt.Println("调整编号:", serr.AdjustmentID) // load-g1
    fmt.Println("说明:", serr)                  // 可直接阅读的中文说明
}
```

```
冲突时有结果返回: false
拒绝原因: 调整编号冲突
调整编号: load-g1
说明: 调整编号 load-g1 已用于不同内容
当前 G1: C1
当前 C1: 已用 30 千克、剩余 70 千克
```

读法：

- 用 `errors.As` 取出 `*stowage.Error`；`Kind == stowage.ErrAdjustmentIDConflict`
  表示这个编号此前已成功用于**别的内容**，与货物不存在、超重等操作
  层面的失败是不同的错误类别。
- `AdjustmentID` 给出**涉及的调整编号**（去掉首尾空白后的值），便于
  在重试、日志、对账中定位是哪一次提交撞了号。
- `ID` 在这类冲突中不指向货物或舱位；读涉及对象前先确认 `Kind`。
- 冲突提交**不返回结果、不改变任何配载**：上例中 `G1` 仍在 `C1`，
  舱位仍是 30/100 千克。

编号不能复用给另一批安排，**另起一个编号**即可正常提交：

```go
_, err = reg.Adjust("unload-g1-v2", []stowage.Op{
    {Kind: stowage.OpUnload, CargoID: "G1"},
})
```

```
新编号提交后：
当前 G1: （未装载）
当前 C1: 已用 0 千克、剩余 100 千克
```

## 第一次就失败的调整不占用编号

重复提交只针对**已经成功**的调整。第一次提交如果失败（操作不合法、
超重、混装冲突等），整次调整不生效，编号也**不会被保存、不被占用**；
把安排修正后沿用同一编号提交，就是一次正常的全新生效
（对应 `Example_adjustFailureDoesNotConsumeID`）：

```go
reg := stowage.NewRegistry()
reg.RegisterCompartment("C1", 20)   // 只有 20 千克
reg.RegisterCompartment("C2", 100)
reg.RegisterCargo("G1", 30, "上海", false)

// 第一次：装进 C1，30 > 20，超重失败。
_, err := reg.Adjust("load-g1", []stowage.Op{
    {Kind: stowage.OpLoad, CargoID: "G1", Target: "C1"},
})
```

```
第一次原因: 超重
调整编号: load-g1
失败后 G1: （未装载）；C1 已用 0 千克
```

把目标改成装得下的 `C2`，沿用 `load-g1` 提交即成功——这不是"取回
旧结果"，因为旧编号下根本不存在已保存的结果：

```go
res, err := reg.Adjust("load-g1", []stowage.Op{
    {Kind: stowage.OpLoad, CargoID: "G1", Target: "C2"},
})
```

```
修正后结果：
调整编号: load-g1
货物 G1: （未装载） -> C2
舱位 C2 重量: 0 -> 30 千克
修正后 G1 所在舱位: C2
```

注意与本文主线区分：

| 情形 | 编号状态 | 再次提交的行为 |
| --- | --- | --- |
| 编号下的调整**首次成功**后，原内容重交 | 已绑定首次结果 | 成功，原样返回首次结果，**不重新装卸** |
| 编号下的调整**首次成功**后，换内容提交 | 已绑定首次结果 | 拒绝（`ErrAdjustmentIDConflict`），配载不变；另一批安排请另用编号 |
| 编号下的调整**第一次就失败**，修正后重交 | 未被占用 | 按正常调整执行，成功则真正改变配载 |

## 与配载规则及其他文档的关系

本文只讨论正式提交的结果与重复提交，配载本身的规则保持不变：一次
调整中的所有操作作为整体按完成后的最终配载统一校验（舱位总重量不得
超过承重、不同目的地共舱须全部允许混装），任一操作不合法整次调整
都不生效；失败既不改配载，也不占编号。

- 正式提交前想先核对一批安排、读懂预计配载与全部拒绝原因，见
  [提交前核对配载安排](preview-check.md)（`Preview` 只读、不占编号）。
- 每条操作本身合法、但最终配载违反承重或混装限制时，正式提交只返回
  一个结构化错误，报哪个舱位、核对哪个对象以及如何看全部原因，见
  [配载被拒绝时怎样读懂错误](adjust-rejection.md)。
- 想改的是货物的重量、目的地或混装许可而不是位置，见
  [更正已登记货物的资料](amend-cargo.md)（`AmendCargo` 不占用调整
  编号，也不影响已成功调整保存的结果）。
